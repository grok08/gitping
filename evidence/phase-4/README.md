Phase 4 is "Real-Time Messaging". A commit still goes to SQLite first through HTTP, and the API then broadcasts the committed row to every connected client in that conversation. A second browser renders it without a reload, a client that was offline catches up from persisted history exactly once, and both clients keep `messages.seq` order.

Client-named commands close the lost-response gap: a retried send resolves to the message the server already stored, and a browser test drops a real response to prove it.

## The WebSocket design

Approach: Hono's Bun adapter. `apps/api/src/realtime/websocket.ts` creates the pair with `createBunWebSocket()` from `hono/bun`. The route upgrades through `upgradeWebSocket`, which calls `server.upgrade(...)` on the Bun server that Bun passes as the second `fetch` argument. `apps/api/src/index.ts` therefore serves `app.fetch` and hands the paired `websocket` handler to `Bun.serve`:

```ts
const { app, hub, websocket } = createServer(db);

Bun.serve({ port, fetch: app.fetch, websocket });
```

The alternative was to write the upgrade by hand in a fetch wrapper. The adapter was chosen because it keeps the endpoint a normal Hono route, so the conversation existence check, the 404, and the socket lifecycle live in the same route module as the rest of the API.

- Endpoint: `GET /conversations/:id/events` (WebSocket upgrade). An unknown conversation is rejected with `404 {"error":"Unknown conversation: ..."}` before any upgrade.
- Registry: `apps/api/src/realtime/hub.ts` is a `Map<conversationId, Set<client>>` with `subscribe`, `unsubscribe`, `publish`, `subscriberCount`, `clientCount`, and `closeAll`. A failing `send` removes only that client; broadcast never throws into the request path.
- Frames: `apps/api/src/realtime/frames.ts` parses client frames (`{"type":"ping"}` only) and serializes server frames (`ready`, `pong`, `error`). Malformed JSON gets an `error` frame and the connection stays open.
- Event payload:

```json
{
  "type": "message.created",
  "conversationId": "conv-engineering",
  "seq": 2,
  "message": {
    "seq": 2,
    "id": "dab3242d-092d-4fd9-aded-3603b81eedf7",
    "author": "grok08",
    "text": "phase four live mwhu3b0a",
    "command": "git commit",
    "createdAt": "2026-11-15T12:51:52.840Z"
  }
}
```

Message ids are generated by the server (`crypto.randomUUID()` inside the command service), never by the client. The event carries the same `MessageRecord` shape the POST response returns, so the client has one render path for HTTP and realtime.

### Broadcast only after the commit

`createCommandService` calls `events.publish(...)` after `write()` returns. `write` is a `db.transaction`, so publish is unreachable for a rolled-back write. Both `POST /conversations/:id/commands` and the compatibility `POST /commands` go through that one service call, so both broadcast. The integration test reads the row back from SQLite at the moment the frame arrives, which is the observable form of "persisted first".

### Ordering

`messages.seq` is unchanged in the schema, and the API now exposes it:

- `GET /messages` and `GET /conversations/:id/messages` include `seq` and stay ordered by it.
- `POST /commands` and `POST /conversations/:id/commands` include `seq` in the returned message.
- every `message.created` frame includes `seq` at both the event and message level.

The browser merges every confirmed message through one function (`mergeMessages`) that de-duplicates by server id and sorts by `seq`. An event delivered out of order is placed by its `seq`, not by arrival; a repeated event collapses to one row.

Two further guards keep that order honest:

- The hook compares the frame's `conversationId` with the conversation the socket belongs to, and `selectConversation` writes the active id synchronously, so a frame from the previous socket cannot be merged into the conversation just opened.
- The sidebar preview carries the `seq` behind it and only advances forward, so an out-of-order event cannot rewind the text under `engineering`.

### Optimistic versus confirmed

There is no optimistic message. Nothing is rendered until the server has a row:

- The broadcast is the primary path, so a message from another client appears without any client-side guess.
- The HTTP response to the sender's own command is the fallback when the socket is down. It is the same confirmed record, and the merge de-duplicates the copy the socket also delivers.
- Because only confirmed messages exist in state, there is no "pending" style, no reconciliation step, and no way to show two copies of one commit.

### Connection lifecycle and reconnect

`apps/web/src/hooks/useConversationSocket.ts` owns one socket per conversation:

| Event | UI state | Behaviour |
| --- | --- | --- |
| initial | `Connecting` | opens the socket |
| `open` | `Live` | resets the attempt counter and runs catch-up |
| `error` | `Reconnecting` / `Offline` | waits for `close` |
| `close` | `Reconnecting` / `Offline` | retries after 500 ms, 1 s, 2 s, 4 s, 8 s, then 10 s, forever |
| `online` | `Live` | retries immediately instead of waiting out the backoff |
| cleanup or conversation switch | — | clears the timer, stops the heartbeat, and closes the socket |

`Offline` is chosen when `navigator.onLine` is false. Sends never wait for the socket: the composer always posts over HTTP, so the app keeps working while disconnected.

### Heartbeat

A socket that never reports `close` is invisible to the browser. `lib/heartbeat.ts` pings every 25 s; only when no ping is outstanding does the next tick send one, and any inbound frame clears the 10 s deadline. If the deadline passes, the client closes the socket itself, which turns a silent stall into the normal reconnect path. That is what lets `Live` mean "the server spoke recently" rather than "nobody told me the socket died".

### Upgrade guard

CORS does not apply to WebSocket upgrades, so the route checks the `Origin` header against the same allowlist HTTP uses (`apps/api/src/allowed-origins.ts`) before upgrading. A disallowed origin gets `403 {"error":"Origin not allowed"}`. A missing header is allowed because scripts and the test clients send none and there are no credentials to protect.

On every `open`, including a reconnect, the client refetches `GET /conversations/:id/messages` and merges it. SQLite is the source of truth, so anything committed during the outage is picked up, and the merge guarantees it appears once. The sidebar preview is refreshed from that history too, so a client that missed a broadcast does not keep a stale preview.

## Schema change: migration 2

Migration 1 is untouched. Migration 2 adds one table and is the only schema change in Phase 4:

```sql
CREATE TABLE command_requests (
  id TEXT PRIMARY KEY,
  conversation_id TEXT NOT NULL REFERENCES conversations(id) ON DELETE CASCADE,
  message_id TEXT NOT NULL UNIQUE REFERENCES messages(id) ON DELETE CASCADE,
  author_id TEXT NOT NULL REFERENCES users(id),
  created_at TEXT NOT NULL
);
```

`UNIQUE (message_id)` keeps the mapping 1:1, and `author_id` is stored now so the replay check does not need a second migration when identity lands. `PRAGMA user_version` is 2, and the health endpoint reports it.

## Failures found and fixed

1. **The reconnect test failed because offline emulation does not close a live socket.** After `context.setOffline(true)`, `.connection-badge[data-connection="live"]` was still present: expected 0, received 1, for 15 s. Chromium blocks new connections but leaves an established WebSocket open. The test now routes that socket through `page.routeWebSocket`, connects it to the real server, and closes it explicitly while the context is offline. The first run of the spec was 2 failed, 1 passed; the raw log from that run was overwritten by the next run and is not reproduced here.
2. **The ordering test hit the 30 s test timeout.** Both clients were opened before the ordering channel existed, so the receiver's sidebar never contained that row and the click waited forever. The channel is now created first, then the receiver opens and selects it.
3. **Screenshots were written as `name.png.png`.** The helper appends the extension; the call sites passed it too. Fixed in all call sites.
4. **`oxlint` warned about reading refs during render.** The socket hook kept its handlers in a ref, and `App` kept the active conversation id in a ref, both written during render. Both are now written from effects.
5. **The sidebar preview stayed stale after a reconnect.** Catch-up merged history but did not refresh the preview, so a client that missed a broadcast showed `No messages yet` next to messages. `refreshMessages` now advances the preview from the newest persisted message.
6. **The heartbeat never timed out.** The first implementation cleared and re-armed the deadline on every ping tick, so silence just kept pushing the deadline out: `bun run test` failed with `pings, then reports a timeout when nothing answers` — expected `timeouts > 0`, received `0`. A tick now pings only when no ping is outstanding, which is what makes the deadline able to expire.
7. **A finished send wiped the next draft.** `handleSubmit` called `setInput("")` when the response arrived, so text typed while that send was in flight disappeared, and the send button went back to disabled with the command gone. The ordering test exposed it: five rapid sends rendered three or four rows and then waited 30 s on a click that could never be enabled, failing two full `check` runs. `App.tsx` now clears only the text that was sent, and five rapid sends are proven by `realtime.spec.ts --repeat-each=3` (12 passed) plus two full runs.

## Hardening pass

Seven issues were fixed on top of the phase commit, all covered by tests:

| Issue | Fix | Test |
| --- | --- | --- |
| A half-open socket looked `Live` forever | `lib/heartbeat.ts`: 25 s ping, 10 s silence deadline, then close and reconnect | 3 heartbeat tests |
| CORS does not guard the upgrade | `allowed-origins.ts` checked on `Origin` before upgrading | 2 HTTP tests |
| A stuck socket could grow Bun's buffer without limit | `hub.publish` closes a client past 1 MiB of buffered output, so it reconnects and catches up | 1 hub test |
| A frame could land in the conversation just opened | compare the frame's `conversationId`, and set the active id in `selectConversation` | typecheck plus the isolated realtime tests |
| The sidebar preview could rewind | preview carries the `seq` behind it and only advances | realtime reconnect test plus review |
| Reconnects retried in lockstep | 20% jitter on each backoff step | 6 client realtime tests |
| Two realtime tests shared `engineering` | each test creates its own channel | 4 realtime browser tests |

Three issues are knowingly left alone, because each would cost a protocol or schema change to cover a failure mode this app does not produce yet:

- **A crash between commit and broadcast** would leave a row nobody was pushed. Closing it properly needs a transactional outbox and a relay loop; reconnect catch-up repairs the symptom. Design: [docs/realtime-outbox.md](../../docs/realtime-outbox.md).
- **Membership checks on the socket** need an identity model. The origin check covers the browser case; any client that can open a socket can still read any conversation id.
- **A `since=seq` catch-up** is an optimisation with no visible benefit at this data size. Design: [docs/realtime-catch-up.md](../../docs/realtime-catch-up.md).

One follow-up remains from the idempotency work: an automatic retry after a lost response is still a human decision. The composer keeps the text and the id, but never resends on its own; a queue or offline send would be the next design. See [docs/realtime-idempotency.md](../../docs/realtime-idempotency.md).

## Remaining risk

- The hub is per process and in memory. With more than one API instance, a client connected to instance A would not see a commit made on instance B.
- Frames are delivered to all clients, including the sender. That is intentional (the sender renders only the confirmed copy), and the client merge makes the duplicate invisible.
- Browser auto-reconnect is proven by closing one socket. A full process restart of the API mid-session was not exercised; the catch-up path is the same one the test proves.
- Read state is still not persisted, so sidebar unread badges keep their Phase 3 behaviour.
